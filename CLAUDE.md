# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Cieljo is a multiplayer online card game in the style of Skyjo. It is a monorepo with two independent apps (there is no root-level tooling):

- `cieljo-backend/`: Rails 8.1 API-only app (Ruby 3.3.5, PostgreSQL, Devise + devise-jwt)
- `cieljo-frontend/`: React 19 + Vite SPA (plain JSX, react-router-dom v7, no TypeScript)

All code, comments, API messages and UI text must be in English. The user communicates in French, so chat replies are in French.

## Deployment

The app is meant to run on Render, described by `render.yaml` at the repository root (a Blueprint: the API as a Ruby web service with `rootDir: cieljo-backend`, one PostgreSQL database, the frontend as a static site with `rootDir: cieljo-frontend` and a rewrite of every path to `/index.html` for React Router). `render.yaml` was validated against Render's JSON schema (https://render.com/schema/render.yaml.json). Production needs `DATABASE_URL`, `SECRET_KEY_BASE`, `JWT_SECRET_KEY`, `FRONTEND_ORIGIN`, the API's own address (`APP_HOST`, or else `RENDER_EXTERNAL_HOSTNAME`, which Render sets on every web service) (API) and `VITE_API_URL` (frontend build). `cieljo-backend/bin/smoke <API address> <frontend address>` checks a deployment from the outside (Ruby standard library only: health check, CORS, sign-up, login, a game, logout, the frontend's routes and the API address built into its JavaScript); it also works against a production server on this computer (`http://` URLs get an `X-Forwarded-Proto: https` header so `force_ssl` does not redirect). Mutation checks (breaking a rule on purpose to see a test fail): clear `tmp/cache/bootsnap` after restoring a file, since Bootsnap keys its cache on the file size and mtime and can keep serving the broken version. To run the API in production mode on macOS, set `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` (Solid Queue forks inside Puma; not needed on Linux).

## Commands

Backend (run from `cieljo-backend/`):

```bash
bin/setup                      # install gems, prepare DB
bin/rails server               # API on http://localhost:3000
bin/rails db:migrate
bin/rails test                                   # all tests (Minitest, parallel, fixtures :all)
bin/rails test test/models/game_test.rb          # single file
bin/rails test test/models/game_test.rb:12       # single test by line
bin/rubocop                    # lint (rubocop-rails-omakase)
bin/ci                         # full CI pipeline: setup, rubocop, bundler-audit, brakeman, tests, seeds (config/ci.rb)
bin/rails "dev:reveal[ABCD]"   # manual testing (development only, lib/tasks/dev.rake): every grid card but one face up
bin/rails "dev:scores[ABCD,95]" # manual testing: set every player's total score (round history unchanged)
```

Frontend (run from `cieljo-frontend/`):

```bash
npm install
npm run dev      # Vite dev server on http://localhost:5173
npm run build
npm run lint     # ESLint
npm test         # Vitest, once (npm run test:watch to rerun on save)
```

Frontend tests (Vitest) cover the pure game logic in `src/game/` (`*.test.js` next to each module, builders in `testHelpers.js`); components are not tested yet.

## Architecture

### Integration between frontend and backend
- All API routes live under `/api/v1` (`config/routes.rb`). `src/api.js` exports `API_URL` (`VITE_API_URL`, set when the frontend is built, see `cieljo-frontend/.env.example`; default `http://localhost:3000/api/v1`), `jsonHeaders` for public requests and `authHeaders()`, which adds the `Authorization` header from `localStorage`. Every page uses them. There is no Vite proxy.
- CORS (`config/initializers/cors.rb`) allows the origins of `FRONTEND_ORIGIN` (comma-separated; default `http://localhost:5173` outside production, required in production), exposes the `Authorization` header and allows no credentials (no cookies).

### Authentication (custom JWT flow, not standard Devise)
- **Sign-up**: `POST /api/v1/users` goes to `Api::V1::Users::RegistrationsController`. Passwords need 8 to 128 characters (`config.password_length`; checked only when a password is set, so older accounts with shorter ones can still log in). `sign_up` is overridden so it does not log the user in through the session.
- **Login**: `POST /api/v1/auth/login` goes to `Api::V1::AuthController#login`. This is a custom endpoint, not Devise's `sessions#create`. It checks the password manually, encodes a token with `Warden::JWTAuth::UserEncoder`, and returns it as `data.token` (already prefixed with `"Bearer "`) in the JSON body, not in a header.
- **Request auth**: `ApplicationController#authenticate_user!` **overrides** Devise's version. It decodes the token from the `Authorization` header with `Warden::JWTAuth::TokenDecoder`, loads the user from `sub`, and checks that `user.jti == payload['jti']` (JTIMatcher revocation). It sets `@current_user`. Every controller requires auth by default. Public endpoints must use `skip_before_action :authenticate_user!`.
- `RackSessionFix` concern: Devise controllers need it in API mode because there is no session store.
- Devise routes: only sign-up is exposed (`devise_for :users, skip: %i[sessions passwords registrations]` + `devise_scope :api_v1_user { post "users" }` in `config/routes.rb`). Inside the `api/v1` namespace, Devise names the mapping `:api_v1_user`, while our tokens are encoded with the scope `:user`: our own flow (`AuthController#login` with `UserEncoder`, `authenticate_user!` with `TokenDecoder` + `jti`) does not depend on that name, but Devise's session routes cannot work with it, so they are skipped. devise-jwt adds default dispatch/revocation paths to its middleware from the mapping; `config/initializers/devise_jwt_requests.rb` clears them after boot, since our own controllers create, check and revoke the tokens (so `DELETE /api/v1/users/sign_out` is a plain 404 instead of crashing in the revocation middleware). Planned later: account edit/delete and "forgot password" as our own endpoints using `current_user`; the `User` model keeps all its Devise modules for that.
- Rate limits (Rails 8 `rate_limit`, answered by `ApplicationController#render_rate_limited` with a 429 JSON error): login 10 per 3 minutes per IP, sign-up 5 per hour per IP, game creation 10 per minute per user. They count requests in `Rails.cache` (memory in development and test, Solid Cache in production); the test cache is cleared before each test.
- Logout: `DELETE /api/v1/auth/logout` calls `User.revoke_jwt` (JTIMatcher): the user gets a new `jti`, so every token issued before is rejected. There is one `jti` per user, so it logs the user out of all their devices. `GET /api/v1/me` returns the logged-in user (`id`, `email`, `username`).
- The JWT secret comes from `ENV['JWT_SECRET_KEY']` (in development, from `cieljo-backend/.env`, git-ignored, loaded by dotenv-rails) or `credentials.jwt_secret_key`. In production the app refuses to start without it. Tokens expire after 1 day.
- Production also requires `FRONTEND_ORIGIN` (CORS) and `APP_HOST` or `RENDER_EXTERNAL_HOSTNAME` (host check), and forces HTTPS (`/up` excluded).
- Frontend: the token and the username are stored in `localStorage` (`token`, `username`). The token is sent as-is in the `Authorization` header. Every authenticated request goes through `apiFetch` (`src/api.js`): on a 401 it clears the local session and opens `/auth?expired=1&next=<current page>`. Sign-up and login use a plain `fetch` (a wrong password must not redirect). The home page checks the stored session with `GET /api/v1/me` when it opens. `components/RequireAuth.jsx` protects `/game/:room_code` (no token → `/auth?next=...`); the login page goes back to `next` (paths of the site only). `logout()` in `api.js` calls `DELETE /api/v1/auth/logout`, then clears the local session even if the request fails.

### Game domain (`app/models`, `app/services`)
- References have foreign keys: `games.current_player_id` (bigint, `ON DELETE SET NULL`), `friendships.friend_id`, `invitations.host_id`/`guest_id` (bigint, deleted with the user by the `User` model). Cards are indexed by `(game_id, location)`.
- `Game` has many `Player`s (the join between `User` and `Game`, with `score` and `turn_order`), `Card`s and `Invitation`s. `Game#current_player` points to a `Player`. On create, `room_code` is generated automatically as a unique 4-character code. `status` is one of `pending | in_progress | round_over | finished`.
- `Card`: `value`, `location` (string, for example `draw_pile`), `is_face_up`, and `row`/`column` for its position in a player's grid. `player_id` is null for draw pile and discard pile cards (`belongs_to :player, optional: true`). Locations in use: `draw_pile`, `player_grid`, `discard_pile`, `hand` (the card the current player has drawn, face up). The deal takes the draw pile in `id` order (the deck is shuffled before insertion); during the turns, `TurnService` draws a random draw pile card, so the pile stays shuffled after being refilled. The top of the discard pile is its most recently updated card; `TurnService#discard!` gives each discarded card a strictly later `updated_at` than the current top, so several cards discarded in one request keep their order.
- Database: production uses a single PostgreSQL database from `DATABASE_URL`. Solid Cache (`Rails.cache`, used by the rate limits) and Solid Queue (background jobs, run inside Puma when `SOLID_QUEUE_IN_PUMA` is set) keep their tables in it, created by regular migrations in `db/migrate`. Action Cable is not used yet (`async` adapter in production; `db/cable_schema.rb` is kept for when real time is added).
- `GameInitializerService` builds the 150-card Skyjo deck (-2×5, -1×15, 0..12×10), shuffles it, and inserts it with `insert_all!`, which skips model validations.
- `POST /api/v1/games` runs `GameCreatorService`: in one transaction it creates the game, adds the current user as player 1, sets `current_player`, then runs the initializer, so a failure leaves nothing behind.
- The host is the player with `turn_order` 1. `POST /api/v1/games/join` adds a player to a `pending` game, under a row lock, up to `Game::MAX_PLAYERS` (8, the official Skyjo limit); `GameStarterService` also refuses more than 8. `GET /api/v1/games/:room_code` returns `max_players`.
- `POST /api/v1/games/:room_code/start` (host only, at least 2 players) runs `GameStarterService`: under a row lock, it deals a 3x4 grid (`row` 0..2, `column` 0..3) of face-down cards to each player, flips the next draw pile card onto the discard pile, sets the game `in_progress` and clears `current_player`.
- Initial reveal phase (`Game#initial_reveal_phase?`: `in_progress` with no `current_player`): each player reveals `Game::INITIAL_REVEAL_COUNT` (2) cards of their grid with `POST /api/v1/games/:room_code/reveal` (`{ card_id }`, `InitialRevealService`). Once everyone has, the player with the highest revealed total becomes `current_player` (tie: lowest `turn_order`).
- Turns (`TurnService`, under a row lock, current player only, after the reveal phase): `POST /api/v1/games/:room_code/draw` (`{ source: "draw_pile" | "discard_pile" }`) puts a card in the player's hand and stores its origin in `games.drawn_from`; an empty draw pile is refilled with the discard pile except its top card. Then `POST .../swap` (`{ card_id }`) puts the card in hand in place of a grid card, which goes to the discard pile, or `POST .../discard` (`{ card_id }`, only for a card drawn from the draw pile) throws the card in hand and reveals a face-down grid card. After either move, if the played card's column holds 3 face-up cards of the same value, the column is removed: its cards go onto the discard pile (above the replaced or thrown card) and the other cards keep their `row`/`column`, so a grid can have gaps. `TurnService#removed_column` (`{ player_id, column, value }`) is returned by the turn endpoints as `removed_column`. Both moves then end the turn: next player in turn order, `drawn_from` cleared, `turn_number` + 1.
- End of the round: the first player whose grid has no face-down card left after their move (removed columns included) sets `games.round_ender_turn_order` (their seat, not a player id, so it survives them quitting; seats are only renumbered in the lobby) and the last round begins (`Game#last_round?`). When the turn reaches or passes that seat again (`Game#round_over_when_turn_passes?`, checked by `TurnService#end_turn` and by `LeaveGameService` when the current player quits), `RoundEndService` reveals every grid card, saves the points of `RoundScoring` as a `RoundResult` per player (`round_number`, `points`, `doubled`: the history) and adds them to `players.score` (the total). If a player reaches `Game::END_SCORE` (100), the game is `finished`; otherwise it is `round_over` with `games.round_ended_at` set. `RoundScoring`: the sum of the grid cards; the round ender's points are doubled when positive and another player has a lower or equal score. `Game#round_scored?` is true between two rounds and at the end of a game won on points, false for a game finished because the others quit (`round_ender_turn_order` cleared).
- Several rounds: between two rounds (`round_over`), each player sends `POST /api/v1/games/:room_code/ready` (`NextRoundService`, under a row lock, sets `players.ready_for_next_round`). The next round starts once everyone is ready, or on any `ready` request after `Game::NEXT_ROUND_DELAY` (30 s, `Game#next_round_at`): each page sends it when its countdown ends, so no background job is needed. The next round deletes the cards, inserts a new shuffled deck (`GameInitializerService`), deals with `GameStarterService.deal` (shared with the first start), increments `games.round_number` and stores the seat of the previous round ender in `games.first_player_turn_order`: once the cards are revealed, that player plays first (`InitialRevealService`; highest revealed total in round 1 or if they quit).
- `GET /api/v1/games/:room_code` (players only) returns `last_round`, `round_ender_id`, `round_scored`, `round_number`, `next_round_in` (seconds left between two rounds, counted by the server), each player's `score` (the total), `rounds` (the history), `ready` (and, once the round is scored, `round_points` and `round_doubled`), `rules` (`grid_rows`, `grid_columns`, `initial_reveal_count`, `max_players`, `end_score`, `next_round_delay`: the frontend reads them with `rulesFromApi` in `src/game/rules.js` and keeps no copy of them; only the SCSS assumes 4 columns for the seat width), `initial_reveal`, `current_player_id`, the `hand` card (with `player_id` and `drawn_from`), the players with their `grid`, the `draw_pile_count`, the `discard_top` card and `discard_recent` (the last 5 discarded cards, oldest first; all discarded cards are public). The value of a face-down card is never sent (`card_json` in `GamesController`).
- Leaving (`POST /api/v1/games/:room_code/leave`, `LeaveGameService`, under a row lock): in the lobby the player is removed and the others are renumbered 1..n (the new number 1 is the host); an empty game is deleted. In a game in progress the player forfeits: their grid cards are deleted with them (`Player has_many :cards, dependent: :delete_all`), a card in their hand goes onto the discard pile (`Game#discard!`, shared with `TurnService`), the turn passes on if it was theirs, the first player is chosen if the reveal is over (`InitialRevealService.choose_first_player_if_everyone_revealed`), and with fewer than 2 players left the game is `finished` (the last player wins). Between two rounds the player is removed, and the next round starts if all the others are ready (fewer than 2 left: `finished`). Pausing a game is just leaving the page: the player stays in it, and `GET /api/v1/games` lists the user's games in the lobby, in progress or between two rounds (most recently active first, with whose turn it is) to come back to them.
- Cleanup: `CleanupInactiveGamesJob` (every hour in production, `config/recurring.yml`) deletes the games where neither the game, nor a player, nor a card changed for `INACTIVITY` (24 hours), whatever their status.
- `Friendship` (self-join on `User`, status `pending|accepted|blocked`) and `Invitation` (`host`/`guest` users) exist only as models for now, with no endpoints.

### Frontend routes (`src/App.jsx`)
- `/` → `pages/Home.jsx` (creates a game or joins one with a room code, then navigates to the room; "My games" lists the user's games)
- `/auth` → `pages/Auth.jsx`
- `/game/:room_code` → `pages/GameRoom.jsx` (polls the game every 3 seconds; shows the lobby on the table while `pending`, then `components/GameTable.jsx`)

### Frontend structure
- `src/pages/`: one component per route. `src/components/`: reusable components (`Card`, `PlayerGrid`, `TableLayout` for the green table and the seats around it (a 3 x 3 grid with the current player at the bottom center and 7 places around, one player per place; `USED_SEATS` gives the places used for 2 to 8 players, filled clockwise in turn order; the middle column is always 420 px and the table is as wide as its content), `RoomCode` shown in its middle in the lobby, `TableCenter` for the piles in its middle during the game, `RoundScores` over the piles once the round is scored (the piles fade out once the last moves have landed): the `ScoreTable` (the total and the points of each round per player; a doubled round reads `6×2`, the card points then the doubling, in bold), then between two rounds a "Ready" button, who is ready and the countdown (`hooks/useCountdown.js`), or at the end of the game a button back home, `InfoButton` in its bottom right corner during the game, whose bubble shows the game message (what to do, whose turn) with a yellow dot when the message changes, and below it each player's total (`ScoreTable` with `light` and `totalOnly`, from the second round on), `GameTable`). `PlayerGrid` shows under each name the points of the round so far (`livePoints`: the face-up cards, then `round_points` once scored). The table keeps the same size when the game starts: the room code fades out, the piles fade in, then the cards are dealt.
- `src/game/`: pure game logic, without React or the DOM, tested with Vitest: `seating.js` (where the opponents sit), `tableChanges.js` (removed columns and departed players between two refreshes), `tableMessage.js` (the info bubble message, with the last round reminder), `roundScores.js` (ranking, winners, last round text, played rounds, round points text, next round countdown text), `liveScores.js` (the points of the round under each name), `deal.js` (the order of the deal), `rules.js` (the rules from the API), `cardLabel.js` (what screen readers say for each card).
- `src/hooks/`: custom hooks. `useDealAnimation` plays the ~10 s deal animation (cards fly from the draw pile with the Web Animations API, then the first discard card flips) when a page sees the game go from `pending` to `in_progress`. It is skipped with `prefers-reduced-motion`.
- `useCardDrag` is a home-made drag and drop with Pointer Events (mouse, touch, pen; no library): a copy of the card follows the pointer, the target is found with `elementFromPoint` and `data-card-id`. During a turn, the card in hand sits on the pile it was taken from and is dragged onto a grid card to swap it; clicking a face-down grid card discards a card drawn from the draw pile and reveals it; before drawing, the discard pile card can be dragged straight onto the grid (draw then swap). Every move can also be played by clicks, so with the keyboard too (clicks go to the card's own `<button>`; `useCardDrag` ignores the click that ends a drag): click the card in hand to select it (`card--selected`, `aria-pressed`), then the grid card to replace (`moveTo` glides the card like a drop); a discard pile card taken with a click is selected at once, since it can only be swapped; without a selection, clicking a face-down card still discards.
- Accessibility: every card has an `aria-label` from `src/game/cardLabel.js` (never the value of a face-down card), a card that cannot be clicked is a `role="img"`, each grid is a named `role="group"`. Form fields have a `<label>` (the `visually-hidden` mixin of `_mixins.scss` hides one the layout makes obvious), and `LeaveGameDialog` keeps Tab inside it and gives the focus back to its opener.
- Leaving: "Leave the table" in `GameRoom` opens `components/LeaveGameDialog.jsx` (lobby: leave; game in progress: "Pause the game" goes home and keeps the seat, "Quit the game" forfeits after a confirmation step); a game finished because the others quit shows a "Game over" screen on the table and is left directly; at the end of a game won on points, "Back to the home page" and "Leave the table" only go home, so the other players keep every score on screen (the cleanup job deletes the game). `GameTable` announces players who left in the info bubble. The home page lists the user's games (`GET /api/v1/games`) with a button to open or resume each one.
- Rounds in `GameRoom`: `GameTable` has `key={roundNumber}`, so each round starts with a fresh table (deal, scores, table changes); the deal animation plays when the page sees `pending` or `round_over` turn into `in_progress`. Between two rounds, `GameRoom` turns `next_round_in` into a local deadline and sends `ready` quietly when it ends (again after each load until the round starts); leaving then opens the same dialog as a game in progress.
- `GameRoom` sends every action through `postAction`, which reloads the game before resolving, and polls the game every 3 seconds while the tab is visible (it stops when the tab is hidden and reloads as soon as it is shown again). Loads can cross, so each load is numbered: an answer is shown only if it is newer than the one on screen (`shownLoadRef`), and the loads started before an action is answered are ignored (`firstValidLoadRef`), so the game never flashes back to an older state.
- `src/utils/`: plain functions that are neither components nor hooks. `prefersReducedMotion` tells whether animations must be skipped. `flyCard` creates a card that flies over the table (fixed element, only `transform` animated, optionally ending edge-on so the real card finishes the flip); it is used by the deal and by `throwToDiscard` (`hooks/useThrowToDiscard.js`), which makes the card thrown onto the discard pile fly there once the move is played (the replaced grid card on a swap, the drawn card on a discard).
- Removed columns: `PlayerGrid` places each card at its `row`/`column` with CSS grid and draws the remaining columns next to each other, centered in a seat as wide as a full 4-column grid (card sizes are SCSS variables in `_variables.scss`), so a grid that loses a column never moves its neighbours. `hooks/useTableChanges.js` (used by `GameTable`) detects a column gone since the previous refresh (for any player), keeps its 3 cards in the grid as `extraCards` while they fly one by one to the discard pile (which shows `discard_recent` landing in order), then the grid closes up with a FLIP animation in `PlayerGrid`. The info bubble says who removed a column until the turn passes again.
- Animations only play in front of the player: `animationsAllowed` (`src/game/animations.js`) is true only when the tab is visible (`hooks/usePageVisible.js`), the game is not catching up, and the user does not prefer reduced motion. `GameRoom` provides it through `contexts/AnimationsContext.js` (`useAnimationsAllowed`); `Card`, `PlayerGrid` and the animation hooks read it instead of checking `prefersReducedMotion` themselves. Back on the tab, the first load is a catch-up (`loadGame({ catchUp: true })`, `catchingUp` in `GameRoom`): what happened meanwhile (deal, removed columns, flips) shows in its final state, then animations are allowed again. Leaving the tab ends every running animation at once (`finishAllAnimations` in `GameRoom`: `document.getAnimations()` + `finish()`, and the deal is stopped); `useTableChanges` drops the removed columns still to animate, and `useThrowToDiscard` does not flip a card that landed while the tab was hidden.
- Card animations rules: animate only `transform`/`opacity`; keep the real card hidden (`card--hidden`, `card--lifted`) while a copy of it moves, and remove the copy only after React has shown the real card (layout effect or two animation frames), so nothing blinks; keep every card of the game the same size (`$card-width` x `$card-height` for grids, piles and flying cards alike, with `box-sizing: border-box`), so a card never changes size in flight and the piles a fixed width, so the table never shifts. `Card` flips over by itself when it turns face up.
- Responsive table: `--card-width` (in `styles/main.scss`) follows the window size with `clamp()`/`min()` (pure CSS, between 28 px and 64 px) so the whole table fits the screen (its height formula keeps 200 px for the fixed-size names and points of the seats). Every size of the table is derived from it with the Sass function `scaled($px)` (`_variables.scss`), which scales a size of the layout designed for 43 px cards; never use a fixed px size for something inside the table that must follow the cards. Below 1400 px wide, the title and the leave button of `GameRoom` go above the table.
- Each component's `.scss` file sits next to its `.jsx` file and is imported by it. `src/styles/` only holds shared SCSS (`_variables.scss`, `_mixins.scss`), used with `@use`.
